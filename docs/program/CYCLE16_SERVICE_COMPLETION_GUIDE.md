## Original sources and public API

- `readServiceCompletionGuide(sources, gate)` returns the SAME original C15
  `ServiceReviewRequests` reference, retained behind a source-currentness fence.
- `selectServiceCompletionContext(view, selectedJobId?)` delegates to C15's exact
  selected-job validation. Invalid/foreign/ambiguous hints reject without fallback.
- `filterServiceCompletionRequests(view, {query, customer_id, location_id,
request_state})` intersects literal text and exact admitted filter identities.
  Rows preserve request/customer/property/job/issued identity. No regex, fuzzy
  relationship, broader customer read or inference from an empty result exists.
- `openServiceCompletionContext(view, {request_id, job_id,
staff_context_confirmed:true})` delegates to C15's original request path and
  returns that SAME retained source object. It does not invent a request/job FK.
- `openServiceCompletionReport(path, reference)` opens the original C15 exact
  published report, then calls original `readCompletionReview` only for an exact
  recorded report-to-selected-job link. Its result contains original `report`,
  `completion`, `selected_job_association` and `completion_status`.
- Property/sibling documentation remains inspectable through the original report
  reader. Its `completion` is null and status is
  `UNKNOWN_REPORT_JOB_LINK_NOT_RECORDED`; it cannot become job-completion evidence.
  Exact recorded links yield `EXACT_READ_ONLY_DOCUMENTATION`, never completion PASS.
- `openServiceCompletionFinding(path, reference)` delegates to the original exact
  report/version/finding/source-position reader. Observations and recommendations
  remain separate, unchanged text.
- `assertServiceCompletionGuideCurrent`, `assertServiceCompletionContextCurrent`
  and `assertServiceCompletionEvidenceCurrent` fence retained references on render
  and navigation. Copied/serialized objects do not confer access.
- `returnServiceCompletionSelection(path)` returns the same original request view
  and exact request/job selection. `selectServiceCompletionJob(path)` validates the
  original existing job before the optional host callback to section `completion`.
  `inspectServiceCompletionContext` exposes CURRENT read-only or terminal UNKNOWN,
  with replay false and replacement null.

The original C12 `required_proof` records arrive through C15's customer-safe path:
scope verification, physical completion, customer acceptance and warranty all remain
UNKNOWN. The original completion reader compares the same issued scope and published
report; scope-line documentation matches remain NOT ESTABLISHED. Its physical
completion, acceptance and warranty remain UNVERIFIED. The existing
`completionReviewChecks` appear as guidance only, with no attestation controls.
No preparation, packet, approval, reservation, publication or writer is invoked.

## Working review and retained return

Stable region/title: **Service completion guide**. Main can mount it in the existing
Customer continuity slot over the same source root. Demo:

1. Enable Main's local guide option and open the existing Customer slot. The host
   selected-job hint preselects its exact admitted request/job context once.
2. Use **Search service requests**, **Service customer**, **Service property** and
   **Request state**. Counts mean available requests/admitted job contexts, never
   complete customer or property history. A literal no-match result stays empty.
3. Choose **Service request and review job**, then explicitly check **I confirm
   this exact job as staff-selected review context.** Select **Open service
   completion context**. The absent recorded request/job FK remains UNKNOWN.
4. Review **Completion requirements (UNKNOWN)** and the original safe Passport
   documentation. **Safe Passport timeline sources** retains original dates, their
   distinct meanings and exact report/job/version identities. **Review exact published report [ID] version [N]** opens the
   original report and, where recorded linkage exists, original completion review.
   **Inspect exact service finding [ID]** opens that exact observation/reference.
5. **Return to published report selection** retains the context. **Return to
   service requests** retains filters and exact selection, while **Resume retained
   completion review** restores the same report/finding without another read.
6. **Open same service job [scope]** is a separate checked callback after report
   inspection. Host navigation can unmount this component; local return guarantees
   apply while it remains retained, not after navigation/reload/new tab.

Filtering does not change the retained selection silently. An excluded selection
requires explicit selection of a visible context before opening a new path. Input
or confirmation changes withdraw old detail. No request/job relationship is created
by choosing a context, matching text, property identity or opening documentation.
Checkmarks, after phase, photos and absence of findings never supply physical proof.
