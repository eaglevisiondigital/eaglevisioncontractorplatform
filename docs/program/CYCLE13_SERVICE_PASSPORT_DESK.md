## Working source navigation

`readServicePassportDesk(sources, {query, customer_id, location_id, job_id, state},
gate)` composes the existing C12 lifecycle/C11 continuity/C10 service-desk/C9 safe
source readers. Literal search covers original request, customer/property, issued
scope, exact source identifiers and recorded job-linked report summaries. Customer,
property, job and recorded request-state filters combine without substituting a
foreign or conflicting selection. Available counts describe three prepared requests,
four jobs, three properties and four published report versions in the existing
fixture environment; they never represent complete CRM or physical-work coverage.
Dependent selectors retain the exact customer/property relationship for each option.

The selection table keeps multiple jobs at one property distinct. Opening one source
retains its actual request, original offer/LOCAL-TEST receipt, estimate, immutable
issued version, customer, property and job identities. The request-to-issued-scope
relationship is explicitly a staff selection; a recorded request/estimate foreign key
and genuine customer approval remain unverified. No request, job or history is created.

`openServicePassportJob(view, exactJobId)` reuses C12's existing customer-safe
allowlist and directly reads the existing `readCustomerWorkflow` Property Passport
timeline. It does not reconstruct a timeline, introduce a second history or change
an existing engine. Recorded issue dates, recorded visit dates, publication time,
report versions and exact recorded report/job relationships retain their original
meaning. Sibling or ambiguous property documentation remains UNKNOWN for the
selected job. No nearest, newest, fuzzy or inferred relationship is used.

`openServicePassportReport(detail, exactReportReference)` opens only the original
property/report/published version through the existing reader. Its published
checklist, observations and recommendations remain separate. The subsequent
`openServicePassportFinding(detail, exactFindingReference)` checks the same report,
version, finding ID and source position. `selectServicePassportJob(detail)` provides
a separately checked existing-job navigation target. The UI shows job navigation
after report inspection and focuses the exact source/report/finding heading.
Back to service selection preserves filters, property context and the retained view.

`inspectServicePassportDesk(view)` reports only how many source identities staff
successfully inspected in that retained view in this tab. Its private Set is ephemeral
reading metadata, with no writer, persistence, workflow stage, attestation or approval.
Reading the same source again does not increment the count. It cannot erase UNKNOWN,
create a new business attempt or establish genuine Auth/durable custody.

## Admission, privacy and missing proof

The exported component defaults OFF. DEV, explicit enablement and literal HTTP
loopback admission precede source getters, input coercion and serialization. The
reader requires explicit local admission and strict bounded own-data filters and
references. Source/container/repository/model identity, current eligible staff,
exact tenant/customer/property/job/issued-version/report/receipt identity and saved
source revisions are fenced after every await, after the final hash and on render.
Mutable or accessor-backed references are rejected without invoking their getters.
Canonical reference equality does not depend on field insertion order.

Observed source/input/admission drift or unavailable read acknowledgement makes that
retained view terminal UNKNOWN. Restoring fields cannot reopen it; copied views and
details confer no navigation authority. The UI immediately withholds stale evidence
and discards late responses after filter/context/model changes. It offers no stage
change, retry command, new ID, operational writer or UNKNOWN-reset control.

The separate `customer_safe` projection contains the existing branded property,
issued scope and published Passport timeline only. Staff request/receipt provenance
stays outside it. Staff notes, costs, prices/rates, suppliers, payroll, assignments,
private findings and other customers are excluded. The same existing C12 requirements
explain missing scope verification, authorized physical completion, genuine customer
acceptance and reviewed warranty eligibility. All remain UNKNOWN. Checkmarks,
after-phase documentation, photos and absent findings never become physical PASS,
acceptance, repair, warranty, contract, work or financial authority.
