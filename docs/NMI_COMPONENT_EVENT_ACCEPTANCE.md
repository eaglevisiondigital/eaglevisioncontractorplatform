## Verified provider contract and implemented limit

The official [Payment Component guide](https://docs.nmi.com/docs/payment-component) recommends that component with the REST API for new integrations. Its [frontend contract](https://docs.nmi.com/docs/integration-guide-implement-frontend) defines onPay events with `token` and optional `lookupData`, and a callback result of `Promise<true | string>`: `true` indicates payment success. Tokens and form completion alone do not establish it.

`receiveNmiComponentOnPayLab` accepts that event shape only with the existing fictional ceremony/lab. It reads own-data token and ceremony primitives, rejects extra fields/accessors/Proxy substitution, and passes the token directly into the accepted lab. Optional lookup metadata is only checked for a top-level own-data descriptor: its descriptor/value is not copied into retained records or traversed/serialized. The adapter releases its event reference before awaiting; it makes no garbage-collection or memory-zeroization claim. The returned immutable result contains only the private reference, `paymentExecuted: false`, `settlement: UNVERIFIED` and a fixed **string** `componentReply`; it never produces SDK success `true`. The privileged reference is not a customer payment receipt.

The same frontend guide defines onChange completion separately and warns that fields can later become incomplete. Initial incomplete editing must not consume a submitted command. This adapter therefore rejects onChange/3DS/express-checkout inputs; it is not a general SDK event listener. A future genuine frontend must implement those ceremonies separately and must not reuse a completed token after an uncertain payment, even if the component resets its fields.

Public SDK examples still contain package/export placeholders. No package name, installation, script/origin permission, token TTL or lookup-data semantics were guessed. The accepted lab's fictional-token and `.invalid` fences, ephemeral custody and lack of cross-process deduplication remain intact. This is not a real Payment Component integration, PCI certification, operational custody or genuine Auth.
